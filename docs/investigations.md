# Investigations

Analyst-style write-ups of the detections triggered in this lab. Each follows the same structure: what fired, what actually happened, whether it is malicious, the response, and how the detection could be tuned. All activity here was generated by me against my own VMs; the "attacker" is the lab's Kali host or a simulation run on the endpoint.

---

## 1. Encoded PowerShell command (rule 100100)

- **Alert:** rule 100100, "PowerShell launched with an encoded command" (level 13)
- **ATT&CK:** T1059.001 (Command and Scripting Interpreter: PowerShell)
- **Host:** win-endpoint (DESKTOP-AJ4SOTQ), agent 002, 10.0.50.20
- **Source:** Sysmon Event ID 1 (process creation)

**What triggered it.** A `powershell.exe` process was created with an `-EncodedCommand` argument carrying a base64 blob. The custom rule matches encoded-command flags in the Sysmon command line and is set to level 13 so it surfaces ahead of the built-in encoded-PowerShell rule.

**What happened.** Decoding the base64 (UTF-16LE) resolves to `whoami; hostname`, two discovery commands. The command itself was benign, but base64 encoding is a common way to hide intent from casual log review, so the technique is worth flagging regardless of payload. The alert carries the full command line and the parent process, which is where triage starts: is the parent a normal launcher, or something unexpected like a browser, an Office app, or a scheduled task?

**Is it malicious?** In this case, yes, and it was me. In the real world encoded PowerShell is not always malicious (some management tooling uses it), but it warrants a look, especially when the parent process is unusual or a download or persistence action happens nearby.

**Response.** Decode the command to establish intent; identify the parent process and the user; check what ran immediately before and after on the same host; if it cannot be explained, isolate the host and reset the user's credentials.

**How to tune.** Legitimate automation can use `-EncodedCommand`. To cut false positives, correlate with parent-process context or a nearby network download (rule 100101) before escalating, or allow-list known-good automation by parent image.

## 2. SSH brute force and successful login (rules 5760, 5763, 5715)

- **Alerts:** rule 5760 "sshd: authentication failed" (repeated), rule 5763 "sshd: brute force trying to get access to the system" (level 10), rule 5715 "sshd: authentication success" (level 3)
- **ATT&CK:** T1110.001 (Brute Force: Password Guessing), then T1078 (Valid Accounts)
- **Host:** linux-endpoint, agent 001, 10.0.50.30
- **Source IP:** 10.0.50.40 (the Kali attacker)

**What triggered it.** A rapid burst of failed SSH logins for the user `labvictim` from a single source (10.0.50.40), followed by a successful login for that same user from the same source. Wazuh's built-in rule 5763 correlates 8 or more failures within 120 seconds into one brute-force alert; rule 5715 then records the successful authentication.

**What happened.** Hydra ran a dictionary attack against `labvictim` and cracked the weak password after roughly 19 attempts, then the credentials were used to log in interactively. The sequence, many failures and one success from one IP in a short window, is the classic signature of a successful password-guessing attack. The success alert is the important pivot: from here on the account should be treated as compromised.

**Is it malicious?** Yes. A burst of failures ending in a success from the same source is rarely benign, and the follow-on interactive login means the attacker now has a foothold.

**Response.** Treat `labvictim` as compromised: disable or lock the account and force a password reset; block or investigate the source IP; review what the session did after login (commands, sudo use, new processes, signs of lateral movement); check whether the password is reused elsewhere. Longer term, disable SSH password authentication in favor of keys, and add rate limiting or fail2ban.

**How to tune.** The built-in brute-force rule is solid as is. In a larger environment, baseline expected login sources and raise the severity when a success follows a brute-force burst from the same IP, a brute-force-then-success correlation is higher fidelity than either alert alone.

## 3. Account added to the local Administrators group (rule 100110)

- **Alert:** rule 100110, "Account added to the local Administrators group" (level 12)
- **ATT&CK:** T1098 (Account Manipulation)
- **Host:** win-endpoint (DESKTOP-AJ4SOTQ), agent 002, 10.0.50.20
- **Source:** Windows Security Event ID 4732

**What triggered it.** A member was added to the local Administrators group, which Windows records as Security Event 4732. The custom rule narrows to the Administrators group specifically, so routine group changes do not alert.

**What happened.** The account `labuser` was created and then added to Administrators. Granting local admin is both privilege escalation and persistence: the account keeps elevated access across reboots. Capturing this depends on the Security Group Management audit policy being enabled, which this endpoint has.

**Is it malicious?** In context, yes. An unexpected new local admin is a strong signal, and here it followed other suspicious activity on the same host (the encoded-PowerShell and scheduled-task events from the same run).

**Response.** Confirm whether the change was authorized (a change ticket, a known admin action). If not: remove the account from Administrators, disable or delete it, and review what it did while elevated. Check for other new accounts or group changes across the environment.

**How to tune.** Pair this with the identity of who made the change (the subject user in Event 4732) and whether that actor is an expected administrator. Additions performed by non-admin or service accounts are higher fidelity and worth a higher severity.
